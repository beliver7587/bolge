一句话定位（背下来）： 这是一个自部署的 HTML5 网页游戏平台，把多款独立小游戏（火柴人派对乱斗、泡泡堂、土豆勇士、弹弹堂等）统一跑在同一域名、同一台服务器下，用 Nginx 按子路径反代到各自的后端服务；并采用"端侧权威运算"架构——所有游戏逻辑在房主设备本地计算，服务器只做消息中转，因此单台 2 核 2G 机器就能支撑上百个房间。

0.1 小白前置知识（名词白话）

如果你第一次接触"服务器/域名/端口/反代"，先读完这一节，后面所有内容都会变得好懂。

① 网页游戏是什么？

不用下载安装，打开浏览器（输入网址或在微信里点开）就能玩的游戏。它本质是网页，靠三种技术运行：

  • HTML：骨架，决定有哪些元素（按钮、画布）。
  • CSS：样式，决定长什么样、什么颜色。
  • JavaScript（JS）：逻辑，决定"按了跳就跳、敌人会动"。游戏画面用 Canvas/WebGL 画在浏览器里。

② 服务器是什么？

一台 24 小时不关机的电脑，放在机房（本项目用的是阿里云 ECS，云上的一台虚拟机）。你的游戏代码跑在上面，全世界的人通过网址访问它。你自己的笔记本关机了网站照样能开，因为服务在云服务器上。

③ IP、域名、端口（用"快递"打比方）

名词白话本项目例子
IP 地址服务器在网络上的"门牌号"8.130.129.18
域名好记的地址，解析到 IP（不用背数字）wy2398.icu
端口一栋楼（服务器）里的"房间号"，不同服务占不同端口22=SSH 远程控制、80=HTTP、443=HTTPS、3000=火柴人后端、8095=土豆勇士
关键直觉： 用户只该访问 443（HTTPS）。游戏后端（3000、8095…）就像公司的"内部办公室"，不能让外人直接敲门，所以只监听 127.0.0.1（本机），外人必须经前台（Nginx）转接才能进。

④ 浏览器和服务器怎么对话？

  • HTTP 请求：你在地址栏输入网址 → 浏览器发一个"我要这个页面"的请求 → 服务器返回 HTML 文件 → 浏览器渲染。一次请求一次回应，完事就断开。
  • HTTPS：加密版的 HTTP。不加它，数据会被窃听/篡改，而且微信、苹果等强制要求 HTTPS，否则扫码打不开。
  • WebSocket：建立一次连接后持续双向通信（像打电话，不是寄信）。实时游戏（你的位置、对手的动作）必须用它，否则每次都用 HTTP 请求会卡死。

⑤ 反向代理（Nginx）是什么？

前台/总机。所有用户只访问 443，Nginx 这个"前台"根据 URL 路径把请求分给内部不同服务：

用户浏览器 │ 只认 https://wy2398.icu (Nginx 前台, 端口443) ▼ ┌──────────── Nginx ────────────┐ │ /pc/ → 转给内部 127.0.0.1:3000 │ │ /td/ → 转给内部 127.0.0.1:8095 │ │ /ppt/ → 转给内部 127.0.0.1:8090 │ └───────────────────────────────┘

好处：① 统一 HTTPS（内部不用各自配证书）；② 隐藏真实端口（黑客看不到 3000）；③ 集中做限流/安全头。

⑥ PM2 是什么？

Node.js 程序的"保姆"：崩溃了自动重启、开机自动启动、随时看日志。没有它，你关掉终端程序就死了。

⑦ Bun 是什么？

一个比 Node 更快的 JavaScript 运行环境，启动快、自带打包。本项目前端用它构建，部分后端用它跑。

2. 整体架构（大白话）

请求链路（真实配置，已在服务器上验证）：

玩家浏览器 / 手机微信 │ HTTPS (443) wy2398.icu ▼ ┌─────────────────────────────────────────────┐ │ Nginx (80→443 强制跳转, SSL 终止, 限流) │ │ 按路径分流: │ │ /pc/ /m/ /socket.io/ → 127.0.0.1:3000 │ │ /test/... → 127.0.0.1:3001 │ │ /ddtank/... → 127.0.0.1:3003 │ │ /api/ → 127.0.0.1:3002 │ │ /ppt/ → 127.0.0.1:8090 │ │ /td/ → 127.0.0.1:8095 │ └───────────────┬───────────────┬──────────────┘ │ (各自端口, 仅本地监听) ┌────────────┴─────────┐ ┌──────────────────┐ │ Bun/Elysia + SocketIO│ │ Node http + ws │ │ (sfp 中转/静态) │ │ (tudou/paopao 等) │ └──────────────────────┘ └──────────────────┘ 全部由 PM2 守护 (crash 自动重启)

关键设计取舍：后端端口绝不暴露公网，只监听 127.0.0.1，所有入站流量必须过 Nginx。这样既隐藏了真实端口、统一了 HTTPS，又能在 Nginx 层集中做限流、连接数限制、安全响应头。

为什么 127.0.0.1 这么重要？ 127.0.0.1 是"本机回环地址"，意思是"只接受来自这台服务器自己内部的连接"。游戏后端绑定它，就等于只对内开门；外网用户（8.130.129.18:3000）直接敲这个门会被拒绝，只能走 Nginx 前台转接。这是第一道天然安全屏障。

2.1 端侧权威运算模式（项目最核心的设计思想）

这是整个平台区别于普通网游的地方。以火柴人/土豆勇士为例，一台"房主"设备（打开大屏的那台电脑）既是客户端又是服务器逻辑端：

角色设备职责
房主端（Host）PC 浏览器大屏运行游戏引擎、算物理/碰撞/战斗、渲染画面、把状态广播给所有人
控制端（Pad）手机浏览器只采集输入（摇杆/按钮）并上报，接收房主发来的画面/商店数据
中转服务器云端 Nginx + WS只按房间转发消息字符串，完全不解析游戏内容
为什么这么设计（面试必答）： 普通网游把"谁打中谁、谁掉血"放在服务器算，服务器又贵又容易成瓶颈；本项目把运算下放给房主设备，服务器只做"微信群转发"，所以一台最便宜的 2 核 2G 服务器能扛上百个房间，成本极低。同时天然防作弊——手机端改不了任何游戏数据，因为它手里根本没有运算逻辑。

3. 开发流程全景（从想法到上线）

一个功能从你脑子里冒出来，到全世界能玩，要走完下面这条流水线。理解这条线，面试时你就能讲清"你到底干了啥"。

1

本地开发（写代码）

在自家电脑上写前端（React/PixiJS 画面）、游戏引擎（物理/碰撞）、后端（中转服务）、手机端（手柄）。此时所有东西跑在 localhost（本机），只有你能访问。
2

本地联调（自己先玩）

电脑开"大屏（房主）"，手机扫电脑上显示的二维码连进来当"手柄"，测试两人能联机、不卡、不闪退。
3

构建 / 打包（Build）

把人类写的 TS/React 源代码，用 Vite/Bun 编译、压缩、混淆成浏览器能直接跑的静态文件（一堆 .html / .js / .css）。就像把"源代码菜谱"做成"成品罐头"。
4

上传（Deploy）

用 SSH/SFTP（安全文件传输）把打包好的文件，连同后端代码，传到云服务器指定目录（如 /opt/tudou）。
5

启动服务

在服务器上 npm install 装依赖，用 PM2 把后端进程起起来，常驻运行。
6

配置反代

在 Nginx 里加一段"路径→后端端口"的规则，并把域名证书接上 HTTPS，让外网能访问。
7

真机验证 & 运维

用手机/电脑打开网址，多人对战实测；之后看日志、续证书、盯监控。出事故就排障（第 7.3 节就是一次真实事故）。
一句话串起来： 本地写完 → 本地联调 → Build 成静态文件 → 上传服务器 → PM2 起后端 → Nginx 反代 + HTTPS → 对外发布。安全（第 7 节）贯穿全程，但第 5 节先讲"没出问题时正常怎么发"。

4.1 火柴人派对乱斗（旗舰项目）

技术栈：TypeScriptReact 18ZustandPixiJS v8 (WebGL)ViteSocket.IOBun + Elysia

4.1.1 中转服务器（index.ts）

服务器只做三件事：托管静态前端、按房间转发 WebSocket、维护房间元数据。转发逻辑（项目自带文档中的核心片段，与代码一致）：

// server/src/index.ts —— 收到消息后只做两种转发
if (CLIENT_EVENTS.has(msg.type)) {
  handleClientMessage(socket, msg, clientIP);   // 操作类消息 → 处理房间逻辑
}
if (HOST_BROADCAST_EVENTS.has(msg.type)) {
  io.to(binding.roomCode).emit('message', msg);  // 房主画面 → 广播给同房间所有人
}
逐行解释：
• CLIENT_EVENTS 和 HOST_BROADCAST_EVENTS 是两个"白名单"集合，里面列着允许的消息类型（比如"移动""攻击""画面状态"）。
• if (CLIENT_EVENTS.has(msg.type))：如果这条消息是"操作类"（如手机发来的按键），就交给 handleClientMessage 处理——比如给它在某个房间"安家"。
• io.to(roomCode).emit('message', msg)：如果是"房主广播的画面状态"，就把这条消息原样发给该房间所有人（io.to(房间号) 是 Socket.IO 的"群发到某房间"语法）。
• 注意：服务器从不解析 game_state 的内容，收到房主发来的状态原样转发——这就是"只传话不运算"。

房间用内存 Map 记账，无需数据库：

private rooms = new Map<string, Room>();          // 房间号 → 房间信息
private bindings = new Map<string, SocketBinding>(); // 连接 → 属于哪个房间/玩家
逐行解释： Map 是 JS 的"键值对"结构（像字典）。第一条把"房间号"映射到"房间对象"（里面有谁、什么状态）；第二条把"每条 WebSocket 连接"映射到"它属于哪个房间/哪个玩家"。因为它们在内存里，速度极快，服务器不需要查数据库就能转发。代价是服务器重启房间就没了——但这无所谓，因为真正的游戏状态在房主设备上。

4.1.2 游戏引擎（GameEngine.ts）—— 全项目最硬核

引擎负责"物理 + 碰撞 + 战斗 + 胜负"，以 60Hz 步进、30Hz 广播。为平台格斗手感，项目自研轻量 AABB 物理而非用 Matter.js：

// 自研物理原因：平台格斗需要精准的"贴地/二段跳/击退"，自研包体更小、控制更直接、性能更优（适配低端主机）
const GRAVITY_RISING = GAME_CONFIG.gravityRising;  // 上升阶段重力更轻（跳得爽）
const GRAVITY_FALLING = GAME_CONFIG.gravityFalling;// 下落阶段重力更大（落得干脆）
const MAX_JUMPS = GAME_CONFIG.maxJumps;            // 二段跳
逐行解释： GAME_CONFIG 是一个"配置对象"，把所有可调参数集中放好，方便调手感。const 表示常量（不可改）。两段重力让跳跃"上去轻、下来重"——这是格斗游戏让操作跟手的经典技巧。MAX_JUMPS=2 就是允许空中再跳一次（二段跳）。

碰撞检测用最简高效的矩形重叠（AABB）：

private aabb(ax, ay, aw, ah, bx, by, bw, bh) {
  return ax < bx + bw && ax + aw > bx && ay < by + bh && ay + ah > by;
}
逐行解释： AABB = 轴对齐包围盒（Axis-Aligned Bounding Box），就是用两个矩形是否重叠来判断"撞没撞上"。(ax,ay) 是矩形 A 的左上角坐标，(aw,ah) 是它的宽高；B 同理。四个条件同时满足（A 的左右都跨过 B、上下都跨过 B）才返回 true，表示重叠。这是 2D 游戏最便宜的碰撞算法。

手感优化细节（这些在面试里非常加分，说明你懂游戏）：

  • 分段重力：上升轻、下落重，跳跃更跟手；
  • 加速度 + 摩擦力：不是一按就满速，而是加速/减速，避免僵硬；
  • 土狼时间（Coyote Time）：离开平台边缘的一瞬间仍允许跳；
  • 跳跃缓冲（Jump Buffer）：落地前提前按跳，落地瞬间自动起跳；
  • 二段跳 / 冲刺无敌帧 / 招架窗口：帧数博弈，参考格斗游戏。

游戏主循环（算→画→发）：

const loop = () => {
  engine.step(now);                    // 1. 算：更新世界（60Hz）
  renderer.render(engine.getState());  // 2. 画：PixiJS 渲染（30~60Hz）
  network.broadcastState(state);       // 3. 发：状态广播给其他人（15~30Hz）
  requestAnimationFrame(loop);
};
逐行解释： 这是游戏每秒跑 60 次的"心跳"。requestAnimationFrame 是浏览器提供的"下一帧回调"，让循环跟着屏幕刷新走。每次循环做三件事：① engine.step 推进物理（移动、碰撞、掉血）；② renderer.render 把新状态画出来；③ network.broadcastState 把画面状态发给其他人。now 是时间戳，用来算"过了多少毫秒"，保证不同设备速度一致。

4.1.3 手机手柄（mobile-client）

手机端不做任何运算，只每秒固定上报 20 次当前按键状态（省流量、稳定），而非每次按键立即发：

useEffect(() => {
  const interval = setInterval(() => {
    network.sendInput({ moveX, jump: jumpQueue, attack: attackQueue, drop });
    jumpQueue = attackQueue = false;   // 发完清空一次性按键
  }, 1000 / 20);                       // 20Hz 上报
}, []);
逐行解释： useEffect(...,[]) 是 React 的"组件一挂载就执行一次"钩子。setInterval(函数, 50) 表示每 50 毫秒（=1/20 秒）执行一次里面的函数，所以叫 20Hz 上报。sendInput 把当前摇杆方向和是否按了跳/攻击打包发给房主。jumpQueue=false 是因为"跳"是一次性动作，发完就要清零，否则会一直跳。1000/20=50 毫秒，即 20 次/秒。

4.1.4 完整数据流（手机按跳 → 大屏跳起，<100ms）

① 手机按跳跃 → ② 20Hz 定时器打包 player_input → ③ WS 发到服务器
④ 服务器查房间，原样转给房主 → ⑤ 房主 GameEngine 算跳跃物理 → ⑥ 房主渲染+广播 game_state
⑦ 服务器转发给房间所有人 → ⑧ 手机收到状态更新 UI
为什么延迟低？ 关键洞察：延迟主要发生在"手机→房主"这一跳。同 WiFi 下 <10ms，所以操作感接近本地。而"房主→手机"只是看画面，玩家对"看"的延迟不敏感。

4.2 土豆勇士（肉鸽生存，最近上线）

技术栈更轻：原生 JSCanvas 2DNode http + ws。架构与火柴人一致（大屏算、手机发输入），但用原生实现、便于快速迭代。下面这段是服务器真实代码（tudou-game/server/server.js）：

// 房间中继：host(大屏) 与 pad(手机) 的角色分离，服务器仅按房间转发字符串
const wss = new WebSocketServer({ server, path: '/ws' });
wss.on('connection', (ws) => {
  ws.on('message', (buf) => {
    const m = JSON.parse(buf.toString());
    switch (m.t) {
      case 'join': {                       // 手机加入房间
        const r = rooms.get(String(m.code));
        if (!r || !r.host) { send(ws,{t:'err',msg:'房间不存在'}); return; }
        if (r.pads.size >= 4) { send(ws,{t:'err',msg:'房间已满'}); return; }
        r.pads.set(seat, ws); ws.role='pad'; ws.seat=seat;
        send(r.host, { t:'pad', seat, name:m.name });  // 通知大屏有人加入
        break;
      }
      case 'ph':                           // pad→host 转发（不解析内容）
        sendRaw(r.host, { t:'ph', seat:ws.seat, m:m.m });
        break;
      case 'hall':                         // host→所有 pad 广播
        for (const pw of r.pads.values()) sendRaw(pw, { t:'hf', m:m.m });
        break;
    }
  });
  ws.on('close', () => {                   // 房主掉线 → 整个房间销毁
    if (ws.role === 'host') { for (const pw of r.pads.values()) send(pw,{t:'err',msg:'大屏已关闭'}); rooms.delete(r.code); }
  });
});
逐行解释：
• new WebSocketServer({server, path:'/ws'})：在已有的 HTTP 服务上挂一个 WebSocket 端点，路径是 /ws。
• wss.on('connection', ws => {...})：每当有人连上来，就拿到一个 ws 连接对象。
• ws.on('message', buf => {...})：收到消息时触发。buf.toString() 把二进制转成字符串，JSON.parse 转成对象 m。
• switch(m.t)：根据消息类型分支。
• case 'join'：手机说"我要进房间"。rooms.get(m.code) 查房间；if(!r.host) 表示房间还没大屏，拒绝。r.pads.size >= 4 限制最多 4 个手机。r.pads.set(seat, ws) 把这个手机连接存进房间的"手柄列表"。最后告诉大屏"有个手机坐了第 seat 号位"。
• case 'ph'：手机发来的操作（pad→host），直接原样转给大屏 r.host。
• case 'hall'：大屏发来的商店/状态（host→所有手机），循环转给每个手机。
• ws.on('close')：连接断开。如果是房主掉线，就通知所有手机"大屏已关闭"并删除房间——因为房主是权威，它没了游戏结束。

手机手柄的摇杆上报（tudou-game/js/pad.js，真实代码）：

// 触摸摇杆 → 归一化坐标 → 发给大屏
function joyMove(e){
  const r = zone.getBoundingClientRect();
  let dx = t.clientX - (r.left + r.width/2), dy = t.clientY - (r.top + r.height/2);
  const max = r.width/2, l = Math.hypot(dx,dy);
  if (l > max){ dx=dx/l*max; dy=dy/l*max; }
  joyX = dx/max; joyY = dy/max;
  send({ t:'in', x:joyX, y:joyY });        // 通过 /td/ws 透传
}
逐行解释： 这是手机上"拖动摇杆"的处理。getBoundingClientRect() 拿到摇杆区域的屏幕坐标和大小。dx,dy 是手指相对摇杆中心的位置。Math.hypot(dx,dy) 算距离（勾股定理）。如果手指超出摇杆圆（l>max），就把方向"夹"在边缘（归一化）。最后 joyX/joyY 是 -1~1 的方向值，连同 t:'in' 发给大屏。注意它发的是方向不是坐标——大屏自己据此移动角色。

玩法：20 波生存、材料=金币=经验、波间商店买/合成武器构筑流派、升级四选一、第 20 波 BOSS 决战。商店和升级界面直接渲染在手机端（大屏算好数据，手机只显示并回传购买/升级指令）。

然后新建一个反代配置（用 nano 或 vim 编辑 /etc/nginx/conf.d/game.conf），内容见第 6 节。写完校验并热加载：

逐行解释：
• nginx -t：最重要的一步。它只检查配置文件有没有写错，不真正生效。配错直接 reload 会让 Nginx 起不来、全站瘫痪。-t 通过会显示 configuration test is successful。
• systemctl reload nginx：让 Nginx 重新读取配置。reload（重载）和 restart（重启）不同——reload 不切断已经在连接的用户，更优雅。

5.4 本项目的自动化脚本（deploy_td.py）

实际部署用脚本完成，避免手工敲命令出错。脚本本质是 SSH 连接 + SFTP 上传 + 远端执行（下面是 deploy_td.py 的真实骨架）：

import paramiko, os
HOST='8.130.129.18'; PORT=22; USER='root'
PASS=os.environ['PPT_SSH_PASS']          # 密码走环境变量，不写死在脚本里
ssh = paramiko.SSHClient(); ssh.set_missing_host_key_policy(paramiko.AutoAddPolicy())
ssh.connect(HOST, port=PORT, username=USER, password=PASS, timeout=25)

# 1) SFTP 递归上传（跳过 .git/node_modules）
sftp = ssh.open_sftp()
for root, dirs, files in os.walk(LOCAL):
    for f in files:
        sftp.put(local_path, remote_path)

# 2) 远端：装依赖 + pm2 启动/重启 + 保存
ssh.exec_command(f'cd {REMOTE} && npm install --omit=dev')
ssh.exec_command(f'pm2 delete tudou 2>/dev/null; cd {REMOTE} && PORT=8095 pm2 start server/server.js --name tudou')
ssh.exec_command('pm2 save')

# 3) 修改 nginx 子路径反代（在 443 server 块插入 location /td/，先备份）
ssh.exec_command(f'cp -f {cf} {cf}.bak.td')
# ... 写入 location 块 ...
ssh.exec_command('nginx -t && nginx -s reload')   # 校验后再热加载
逐行解释：
• import paramiko：paramiko 是 Python 的 SSH 库，让脚本能像人一样 SSH 登录、传文件。
• os.environ['PPT_SSH_PASS']：从环境变量读密码，而不是把密码明文写进代码（避免泄露、也避免提交到 Git）。
• set_missing_host_key_policy(AutoAddPolicy())：首次连陌生服务器自动接受它的"指纹"，否则脚本会卡住问你 yes/no。
• ssh.connect(...)：建立连接，timeout=25 秒超时防卡死。
• sftp.put(...)：把本地文件传到远端对应路径（os.walk 遍历文件夹实现递归上传）。
• 2>/dev/null：把错误输出丢掉（pm2 delete tudou 在第一次部署时进程还不存在会报错，丢错误不影响后续）。
• cp -f ... .bak.td：改 nginx 配置前先备份，出问题能还原。这是运维铁律。
• nginx -t && nginx -s reload：先校验，通过后发信号平滑重载。

6. 反向代理 Nginx 详解

所有对外服务都经 Nginx。下面都是服务器上正在运行的真实配置。

子路径分流（生产环境核心片段）

# /etc/nginx/conf.d/stick-fight-party.conf —— 真实生效配置
location /pc/ {                 # 火柴人 PC 端静态
    alias /opt/stick-fight-party/frontend/current/pc/;
    try_files $uri $uri/ /pc/index.html;   # SPA 回退
}
location /m/  { alias /opt/stick-fight-party/frontend/current/mobile/; ... }
location /socket.io/ {                    # WebSocket 透传
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_read_timeout 86400s;             # 长连接，避免秒断
    proxy_buffering off;                   # WS 不能缓冲
}
location /td/ {                 # 土豆勇士（整站反代）
    proxy_pass http://127.0.0.1:8095/;    # 末尾斜杠：去掉 /td 前缀再转发
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;
}
逐行解释：
• location /pc/：当浏览器请求的 URL 路径以 /pc/ 开头，就走这段规则。
• alias：把 URL 路径映射到服务器上的真实文件夹。外面访问 /pc/index.html，实际读的是 /opt/.../pc/index.html。
• try_files $uri $uri/ /pc/index.html：先试"精确文件"，再试"目录"，都没有就回退到 index.html。因为前端是单页应用（SPA），用户直接刷 /pc/room/123 这种前端路由时，服务器没这文件，必须回退到 index.html 让前端自己处理——少这一句会刷新 404。
• proxy_pass http://127.0.0.1:3000：把请求"代理"给内部 3000 端口的服务（WebSocket 专用）。
• proxy_http_version 1.1：WebSocket 必须 HTTP/1.1。
• proxy_set_header Upgrade/Connection：把"升级为 WebSocket"的握手头转发给后端，否则握手失败（见 6.2）。
• proxy_read_timeout 86400s：等后端响应的最长时间设为 1 天，否则游戏长连接会被默认 60 秒掐断。
• proxy_buffering off：关掉缓冲，消息实时透传（缓冲会让实时消息延迟）。
• location /td/ 的 proxy_pass ...:8095/：末尾的斜杠很关键——它表示"把 /td/ 这个前缀剥掉再转发"。用户访问 /td/foo，后端收到的是 /foo。没这斜杠，后端会收到 /td/foo，路径对不上。

6.1 为什么用子路径而不是子域名？

维度子路径（本项目采用）子域名
HTTPS 证书一张证书覆盖全站，成本低每个子域都要证书（或用泛域名）
微信扫码同域同源，扫码跳转无障碍需额外配置，HTTP 限制更严
运维一个 server 块管全部多个 server 块
缺点后端要正确处理基础路径（base href）、cookie 路径隔离更干净，便于独立扩容
面试话术： "我选子路径主要是为了微信扫码必须 HTTPS 同源和一张证书管全部这两点；代价是前端构建要带 base path、Cookie 要注意 path。如果日后某个游戏流量暴涨需要独立扩容，我会把它拆成子域名 + 独立后端实例，Nginx 只需加一个 server 块，改动很小。"

6.2 WebSocket 透传（最容易踩坑的点）

WebSocket 握手是 HTTP Upgrade，Nginx 必须显式转发这两个头，否则握手失败：

map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection $connection_upgrade;
proxy_http_version 1.1;     # WS 必须 HTTP/1.1
proxy_read_timeout 86400s;  # 长连接，否则 60s 默认超时断线
proxy_buffering off;        # 关缓冲，消息实时透传
两个真实坑： ① 漏掉 Connection $connection_upgrade → 握手 400/断连；② proxy_read_timeout 用默认 60s → 玩家挂机一会儿就掉线。本项目直接设成 86400s（1 天）配合后端心跳，彻底解决。

6.3 HTTPS、缓存与安全头

# HTTP 全量 301 跳转 HTTPS
server { listen 80; server_name wy2398.icu; location / { return 301 https://$host$request_uri; } }

# HTTPS：TLS1.2/1.3 + HSTS + 安全响应头
ssl_certificate /etc/letsencrypt/live/wy2398.icu/fullchain.pem;
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "SAMEORIGIN" always;

# 缓存策略：HTML 不缓存（保证发版即时生效），哈希资源缓存 1 年
location ~* \.html$ { add_header Cache-Control "no-cache, no-store, must-revalidate"; }
location ~* \.(js|css|png|...)$ { add_header Cache-Control "public, max-age=31536000, immutable"; }
逐行解释：
• return 301 https://...：所有用 http 访问的人，永久跳到 https 版本（301=永久重定向）。
• HSTS（Strict-Transport-Security）：告诉浏览器"接下来一年只准用 HTTPS 访问我"，防中间人降级攻击。
• X-Content-Type-Options nosniff：禁止浏览器"猜"文件类型，防某些 XSS。
• X-Frame-Options SAMEORIGIN：只允许同源网页把我嵌进 iframe，防点击劫持。
• 缓存：\.html$ 用正则匹配所有 html，设 no-cache 让它每次都拉最新（发版秒生效）；带 hash 的 .js/.css 设 1 年缓存——因为内容变了文件名就变，缓存旧文件不会被引用到。

这套缓存策略是前端发版"秒生效"的关键：带 hash 的文件名（index-a1b2.js）内容变才变，可放心长效缓存；index.html 不缓存，永远拉最新。

7. 网络安全

网络安全 = 保护服务器不被入侵、不被滥用、服务不中断。本项目的防护分三层：云安全组 → Nginx 边界 → 应用层校验。

7.1 三层防护（白话）

层作用本项目做法
① 云安全组（最外层防火墙）决定"谁能敲门"只放行 80/443 入站；游戏端口（3000/8095…）仅在 127.0.0.1 监听，外网根本敲不到
② Nginx 边界统一收口 + 限流单 IP 限流 10 次/秒、WS 连接数限 5、禁大包、禁隐藏文件、加安全响应头
③ 应用层校验防乱发消息/刷接口消息格式校验、单 IP 频率限制、黑名单、全局异常捕获、空房 5 分钟自动清理、房间总数上限
为什么三层？ 任何一层都可能漏，多层叠加才稳。比如安全组挡住了"直接敲 3000 端口"的人，但挡不住"通过 443 正常进来的恶意请求"，所以 Nginx 要限流、应用层要校验。

7.2 SSH 是什么（为什么它坏了最要命）

SSH（Secure Shell）是你远程控制服务器的唯一正常通道——部署、看日志、改配置全靠它。可以把它理解成"服务器的远程桌面/命令行通道"。SSH 一坏，你就进不去服务器了，只能靠云厂商的 VNC 控制台（网页版"紧急通道"）救场。

认证方式说明安全性
密码登录输入 root 密码方便但易被暴力破解
密钥登录本地放私钥、服务器放公钥，免密且极难伪造推荐（本项目那个 AI 用的就是密钥）
相关配置（在 /etc/ssh/sshd_config）： PasswordAuthentication yes/no（是否允许密码）、PermitRootLogin yes/no（是否允许 root 直接登）、UseDNS yes/no（连接时是否做反向 DNS 查询）。改这个文件后必须 sshd -t 校验 + 重启 sshd 才生效，而且改之前最好先备份。

7.3 UseDNS 事故完整复盘（真实发生）

某次"网络加固"后，任何人（包括部署脚本）都 SSH 不上服务器，现象是TCP 能连上 22 端口、但 sshd 迟迟不发 SSH banner，所有客户端在握手前卡死。排查过程（用三种方式从本机探测）：

# 1) 确认不是端口/防火墙问题：TCP 通，但 banner 挂起
#    用原始 TCP 抓 banner → 连接建立后 Read 超时，说明 sshd 接受连接但不发握手包
# 2) 排除改端口：扫描 22/2222/2200/2022... 只有 22 在监听

# 3) 登录云厂商 VNC 控制台（SSH 进不去时唯一的口子），怀疑 SSH 握手前卡在反向 DNS 查询
sshd -t                                  # 配置语法 OK，无报错
sudo sed -i 's/^#*UseDNS.*/UseDNS no/' /etc/ssh/sshd_config
systemctl restart ssh                    # 重启后立刻恢复

# 4) 验证：auth.log 出现 Accepted password / publickey，部署脚本 SFTP 恢复
逐行解释与根因：
• sshd -t：校验配置语法（没报错说明不是写错）。
• sed -i 's/^#*UseDNS.*/UseDNS no/'：这是"就地替换"命令。把以 UseDNS 或 #UseDNS 开头的行，整行改成 UseDNS no。^#* 匹配行首零个或多个 #（兼容被注释的默认值），.* 匹配整行其余内容。
• systemctl restart ssh：重启 ssh 服务使配置生效。
• 根因： 服务器开了 UseDNS yes（默认值），每次有人连 SSH，sshd 都会先做"这个 IP 反向查域名"的操作；而本机 DNS 解析不通，查询卡住 → sshd 不发 banner → 所有人卡在握手前。改成 UseDNS no 跳过这步，立刻恢复。
• 那个 AI 用的是密钥登录，之前也被卡死是因为 sshd 在发 banner 之前就卡住了——密钥和密码都救不了，必须先修 sshd 本身。
结论 & 复盘： 这是"想做安全加固却把自己锁门外"的典型。教训：① 改 sshd 前先备份、改完一定开一个新终端测试能不能连上再关旧连接；② 排障从"分层"入手——先网络层（TCP 通不通）、再应用层（banner/握手）、最后认证；③ 云厂商 VNC 控制台是最后兜底，SSH 进不去时永远能靠它。

7.4 正确加固（别再踩坑）

想真正提高安全性又不破坏 SSH，按这个顺序做：

1

先关掉 UseDNS 这个隐患

sed -i 's/^#*UseDNS.*/UseDNS no/' /etc/ssh/sshd_config
放在加固第一步，因为它单独就能避免本次事故。
2

用密钥替代密码

把你的公钥追加进 ~/.ssh/authorized_keys，确认能用密钥登录后，再设 PasswordAuthentication no。顺序反过来会把自己锁外面。
3

校验 + 测试 + 再关旧连接

sshd -t && systemctl restart ssh
重启后另开一个终端试连，成功才放心。绝不在没验证新会话能连的情况下断开当前连接。
4

依赖安全组而非暴露端口

安全组只开 22/80/443；游戏端口始终绑 127.0.0.1。即便 sshd 出事，游戏服务也不受影响（本项目正是如此——SSH 卡死时网页游戏照常能玩）。
加固 ≠ 乱改配置。 真正有效且安全的做法是：密钥登录 + 安全组最小开放 + 定期更新 + 证书自动续期。本项目当前就是这套，稳定且符合"网络安全"的本意。

8. 面试高频 & 刁钻问答

Q1：你这个"端侧权威"架构，如果房主掉线/作弊/手机和房主状态不一致怎么办？
答：房主掉线时服务器会收到 WebSocket close，立即销毁房间并通知所有手机"大屏已关闭"——因为房主是权威源，它没了游戏就无法继续，这是该架构的固有取舍。作弊方面反而更安全：手机端没有任何运算逻辑，改本地数据没用，所有判定都在房主。至于一致性：手机不跑物理，只接收房主每帧广播的状态来显示，所以天然不会出现"你说打中、我说没打中"的分歧（这正是状态同步 vs 帧同步的区别，我们选了状态同步里最省服务器的一种）。代价是房主网络差会拖垮全房间——所以对房主端做了 30Hz 广播 + 输入 20Hz 上报的带宽控制。
Q2：单台服务器怎么扛上百房间？瓶颈在哪？怎么演进？
答：因为服务器只转发不运算，CPU/内存开销极低（实测单进程 ~50-65MB，2 核 2G 跑 6 个进程还不到 41% 内存）。瓶颈首先是单房主端的性能（房主设备决定一局流畅度），其次才是服务器带宽。演进路径：① 多实例——把不同游戏/不同房间分散到多台后端，Nginx 按路径或一致性哈希分流；② WebSocket 水平扩展需要粘性问题（同房间连同一台），可用 Redis 适配器做跨进程广播；③ 最终上容器 + K8s，按房间数弹性扩缩。
Q3：WebSocket 在 Nginx 后怎么做水平扩展？粘性是啥？
答：默认 Nginx proxy_pass 不保证同房间连同一后端。要扩展需：① IP/房间哈希做粘性（同一房间落到同一后端）；或 ② 用 Socket.IO Redis Adapter / NATS，让多个无状态中转节点通过消息总线互相广播房间消息，这样任意节点收到消息都能转发给全房间。本项目房间在内存 Map，单机内转发即可，还没到跨机阶段。
Q4：为什么不用 Docker？直接裸跑 PM2 不专业吧？
答：这是取舍。Docker 的好处是环境一致、易迁移，但对单机小项目反而增加复杂度（守护、卷、网络）。PM2 在 Node 生态里做进程守护、日志、开机自启已经够用，且和 Bun 配合简单。如果项目要上多机/CI/CD 自动发布，我会引入 Docker Compose 或 K8s——架构是分层的，加容器只是把"进程"换成"容器"，Nginx 反代那一层几乎不动。我会如实说这是成本与复杂度权衡，不是不会。
Q5：游戏延迟怎么处理？100ms 手感不会很差吗？
答：关键洞察：延迟主要发生在"手机→房主"这一跳（同局域网/同 WiFi 下 <10ms，跨公网几十 ms），而"房主→手机"只是看画面延迟，玩家对"看"的延迟不敏感。手机上报的是输入状态而非位置，房主本地立即响应，所以操作感接近本地。跨公网时还会丢包，故用 20Hz 固定上报 + 房主 60Hz 本地模拟来平滑。
Q6：前端用 Bun 构建、后端用 Bun 跑，和 Node 比优势在哪？踩过坑吗？
答：Bun 启动快、内置打包/测试、兼容 Node API，构建速度明显优于 Node+npm。坑：① 个别 Node 原生模块在 Bun 下需要兼容处理；② 生产用 Bun 跑长驻服务要确认稳定性，本项目 sfp 用 Bun、tudou 用 Node，是务实混用。我会强调：工具选择服务于交付效率，不是炫技。
Q7：你这个算"全栈"吗？你最擅长哪层？
答：算，且是端到端：从前端 React/PixiJS、游戏引擎物理、WebSocket 协议设计、Node/Bun 后端中转、到 Nginx 反代与服务器运维都自己搞定。我最能讲透的是实时 multiplayer 的架构设计（端侧权威 + WS 中转）和部署/反代/排障这一整条链路，因为这些都是我实际踩过坑、跑在公网真机上的。
Q8：如果让你重做，哪里会改？
答：① 房主掉线体验——加"房主转移/观战托管"而非直接散房；② 把中转服务做成无状态 + Redis 适配器，为水平扩展铺路；③ 静态资源上 CDN，减轻单台带宽；④ 引入基础设施即代码（Docker/CI），让部署可重复；⑤ 后端服务不要用 root 跑，降权更安全（这也是我从安全加固里学到的）。
Q9：你这个发版后用户为啥不会拿到旧 JS？
答：因为构建工具（Vite）对产物做了内容 hash 命名（如 index.a1b2c3.js），内容一变文件名就变。index.html 不缓存永远拉最新，它里面引用的就是新 hash 的 JS 路径——所以旧文件即使还缓着也不会被引用到。这是前端发版"秒生效且可长效缓存"的标准做法。
Q10：Nginx 反代 WebSocket 时，连接数和超时你怎么设的，依据是什么？
答：单 IP limit_conn 5 防一个 IP 开太多房间刷连接；proxy_read_timeout 86400s 是因为游戏 WS 是长连接，默认 60s 会把挂机玩家踢掉，配合后端 30s 心跳保活；proxy_buffering off 因为游戏消息要实时，缓冲会引入延迟。这些都是从"玩家掉线""消息卡顿"的真实工单里调出来的。
Q11（刁钻）：你说端侧权威省钱，那房主作弊改内存不就无敌了？你怎么防？
答：承认这是该架构的软肋——房主确实是"法官"，能改自己本地的运算结果（比如让自己无敌）。应对分场景：① 休闲/好友局：风险可接受，作弊只影响自己房间，不影响他人，靠社交约束；② 想认真防：可以把"关键判定"（伤害/胜负）移到一个轻量权威节点（比如房主之外再选一个旁观校验端，或关键事件上链/上服务器验签），但那会牺牲"单台扛百房"的成本优势。我会坦诚这是成本与信任的权衡，不是没考虑到，而是当前阶段有意取舍。这反而体现你对"架构没有银弹"的理解。
Q12（刁钻）：你的服务器才 2 核 2G，真有上百人同时玩会不会炸？你怎么证明？
答：证明靠实测数据而非嘴说：① pm2 报告单进程常驻内存 ~50-65MB，6 个进程合计不到 41% 内存；② 因为服务器只转发字符串（每条消息几十到几百字节），CPU 主要耗在加密/网络 IO，2 核足够；③ 真要验证可以做压测（比如用 artillery/wsbench 模拟 N 个房间并发收发），看 p99 延迟和 CPU 曲线。我会主动说"规模再上一个量级我会引入前面讲的 Redis 适配器 + 多实例"，展现 scalability 意识。
