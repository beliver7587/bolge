供应商抽象

把“用哪家大模型”从业务里抽出来 —— 换 OpenAI/国产模型只需改配置，不重写代码。学完你能让 AI 应用不被一家厂商绑死。

1. 这是什么

供应商抽象 是设计模式：定义一个统一的接口（如 chat(messages)），再为每家大模型写实现，业务代码只依赖接口，不依赖具体厂商 SDK。

一句话：业务说“去聊天”，至于用 OpenAI 还是 DeepSeek 去聊，由配置决定。

2. 为什么需要

  • 各家 API 参数、返回结构不同，直接调会写死。
  • 价格/稳定性波动，需要能随时切换或做降级（一家挂了换另一家）。
  • 合规要求用国产/私有模型。

3. 定义接口

// llm/provider.js
export interface LLMProvider {
  chat(messages: {role:string; content:string}[]): Promise<string>;
  stream(messages: any[]): AsyncIterable<string>;
}

4. 实现两家

// openaiProvider.js
import OpenAI from 'openai';
export class OpenAIProvider implements LLMProvider {
  constructor(key) { this.c = new OpenAI({ apiKey: key }); }
  async chat(messages) {
    const r = await this.c.chat.completions.create({ model:'gpt-4o-mini', messages });
    return r.choices[0].message.content;
  }
}
// 再写一个 DeepSeekProvider，同样实现 LLMProvider（内部换 baseURL/模型名）

5. 工厂切换

function createLLM() {
  const name = process.env.LLM_PROVIDER || 'openai';
  if (name === 'openai') return new OpenAIProvider(process.env.OPENAI_API_KEY);
  if (name === 'deepseek') return new DeepSeekProvider(process.env.DEEPSEEK_KEY);
  throw new Error('未知供应商');
}

6. 实战

业务层只写 const llm = createLLM(); await llm.chat(messages)。要换厂商，只改环境变量 LLM_PROVIDER，代码一行不动。

7. 常见坑

坑 1：只抽象了 chat 没抽象 stream，切换时发现一家不支持流式；把常用能力都纳入接口。
坑 2：没统一“消息格式”，某家用 content 某家用数组；在接口层归一。
坑 3：错误没兜底，一家超时直接 500；加超时 + 自动切备胎。
坑 4：把 Key 写死，失去抽象意义；配置化。
