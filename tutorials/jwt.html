JWT：从小白到资深

JWT（JSON Web Token） 是无状态的登录凭证：登录成功后签发一个自包含令牌，客户端后续携带，服务端验签即知身份，无需查库存会话。本教程讲透令牌结构、签名算法与算法混淆攻击、签发校验、刷新令牌旋转、攻击向量、存储防护与 OAuth2 区别——前后端分离身份认证的底线。

1. 它解决什么问题

传统 Session 把登录态存服务端（内存/Redis），横向扩展要共享存储。JWT 把状态编码进令牌本身，服务端无状态、易扩展。

代价：令牌一旦签发无法主动吊销（除非维护黑名单或短过期），这是无状态的固有取舍。

2. 令牌结构

header.payload.signature 三段 base64url：

  • header：{alg, typ}，声明算法。
  • payload：业务数据（userId、exp 等）；任何人可 base64 解码看到，绝不能放密码。
  • signature：对前两段的签名，防篡改（改 payload 验签即失败）。

3. 签名算法

算法特点适用
HS256对称，同一密钥签名/验证单团队、密钥好保管
RS256/ES256非对称，私钥签、公钥验多服务/第三方验证、可公开公钥
算法混淆攻击：若服务端只配 HS256 却用公钥文件当 HMAC 密钥，攻击者可把 alg 改成 HS256 用公钥签名伪造令牌。对策：服务端固定并显式校验 alg，绝不“按令牌声明的算法验签”。另禁用 alg:none。

4. 签发与校验

import jwt from 'jsonwebtoken';
const token = jwt.sign(
  { userId: 1, name: '小王' },
  process.env.JWT_SECRET,    // 服务端密钥，env 注入，足够随机
  { expiresIn: '2h', issuer: 'my-app' }
);

function auth(req, res, next) {
  const token = req.headers.authorization?.split(' ')[1];
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET, { issuer: 'my-app' });
    next();
  } catch { res.status(401).json({ msg: '未登录' }); }
}
资深：verify 时校验 exp、iss、aud，并固定算法白名单。

5. 刷新令牌

  • 访问令牌短命（如 15m~2h），被盗用窗口小。
  • 刷新令牌长效，存 HttpOnly Cookie，访问令牌过期时换发新令牌（旋转：每次用旧 refresh 换新的，并作废旧的，防重放）。
  • 吊销：refresh 可进库（用户登出/改密即作废），而 access token 靠短过期自然失效。

6. 攻击向量

  • 重放：截获令牌在过期前重用；可加 jti+短期黑名单/nonce。
  • 密钥泄露：任何人可伪造；泄露即轮换并作废在飞令牌。
  • 算法降级：见 §3，固定 alg 可防。
  • 弱密钥：HS256 用弱口令 → 暴力破解；用长随机密钥。

7. 存储与防护

位置风险
localStorage易被 XSS 窃取 → 用 CSP 收紧、尽量不用
HttpOnly Cookie防 XSS 读，但要防 CSRF（SameSite + 双重提交）
密码存储：口令用 bcrypt/argon2 加盐哈希，永远不存明文、不进 JWT。

8. 与 OAuth2 / OIDC

JWT 是令牌格式；OAuth2 是授权框架（常用 JWT 作 access token），OIDC 在其上做身份认证。自研登录用 JWT 即可；接入第三方登录（微信/Google）走 OIDC。

9. 常见坑

坑 1：密钥写死/泄露 → 伪造令牌；env 注入且足够随机。
坑 2：payload 放密码 → base64 一解码就暴露。
坑 3：过期太长 → 短过期 + refresh。
坑 4：token 存 localStorage 被 XSS 偷 → 敏感用 HttpOnly Cookie。
坑 5：不固定 alg → 算法混淆伪造。
坑 6：JWT 无法主动吊销 → 关键场景用黑名单或短过期 + 版本号。
