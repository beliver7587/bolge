Next.js：从小白到资深全栈

Next.js 是 React 的生产级框架：约定式路由、混合渲染、API 路由、构建优化一应俱全。本教程带你从“能跑起来”走到“能设计可扩展的全栈架构”，理解它每个默认行为背后的权衡，而不只是背命令。

1. 它解决什么问题

纯 React + Vite 是 CSR（客户端渲染）：浏览器先下载空 HTML 再拉 JS 画页面——首屏慢、SEO 差、要自己接路由/SSR/API。Next.js 把这些“生产必备但重复造轮子”的事收进框架。

一句话：Next.js = React + 路由 + 混合渲染 + API + 构建优化 + 部署约定。让你专注业务，不必在“怎么把 React 做成网站”上耗散。
  • 约定优于配置：app/page.tsx 就是一个路由，少写胶水代码。
  • 渲染策略可选：同一项目里，营销页用 SSG、仪表盘用 SSR、后台用 CSR，按需取。
  • 全栈一体：页面里能直接写 Server 逻辑、Server Actions、Route Handlers，前后端同一仓库。
适合：需要 SEO 的内容站、带后端的全栈应用、电商/营销页、SaaS 控制台。
不适合：纯内部后台（CSR + Vite 更轻）、超简单静态页。

2. 工程化起步

1

创建项目

npx create-next-app@latest myapp --ts --app --tailwind --eslint
cd myapp && npm run dev

选项含义：--ts 用 TypeScript；--app 用 App Router（新项目默认）；--tailwind 接 Tailwind；--src-dir 把代码收进 src/。

2

目录约定

app/
├─ layout.tsx        # 根布局（HTML/全局Provider）
├─ page.tsx          # 首页路由
├─ about/page.tsx    # /about
├─ blog/[slug]/page.tsx  # 动态路由
├─ api/              # Route Handlers（可选）
└─ globals.css

app/ 下的文件夹即路由段；page.tsx 是可视页，layout.tsx 是包裹它的外壳。

3

跑起来看三个信号

① 控制台打印编译耗时（Rust 编译器很快）② 页面源码里能看到服务端已经渲染好的 HTML（右键“查看网页源代码”不是空壳）③ 改文件热更新。

版本号：App Router 自 Next 13.4 稳定，13 之前是 Pages Router（pages/）。本教程只讲 App Router；老项目迁移见官方 codemod。

3. App Router 路由

路由即文件系统，URL 路径 = 文件夹路径。

  • 静态段：app/dashboard/page.tsx → /dashboard。
  • 动态段：app/blog/[slug]/page.tsx，组件中通过 params.slug 取；多个用 [...slug] 捕获剩余。
  • 布局嵌套：每个文件夹都能有 layout.tsx，它包裹该段下所有页面。<Outlet/> 的等价物是“直接渲染 children”，父布局在切子页时不重挂载。
  • loading / error / not-found：同名文件自动变成 Suspense 骨架屏、错误边界、404 页。
// app/blog/[slug]/page.tsx
export default async function Page({ params }: { params: { slug: string } }) {
  const post = await getPost(params.slug);   // 直接在 Server Component 取数
  return <article>{post.title}</article>;
}
资深用法：把“侧边栏/顶栏”放 layout.tsx，“内容”放 page.tsx，切页时布局不闪、状态不丢；用并行路由 @slot 还能在同一布局里独立加载多块。

4. 渲染策略全景

Next 的“强”在于按页面选渲染方式，而不是一刀切。

策略何时渲染适合SEO
SSG / 静态构建时生成博客、文档、营销页优
SSR / 动态每次请求个性化、实时数据优
CSR浏览器端登录后台、强交互差（需额外处理）
ISR静态 + 后台定时重生电商商品页（量大但偶尔变）优
// 静态：构建时取一次
export const dynamic = 'force-static';
// 动态：每次请求都跑
export const dynamic = 'force-dynamic';
// ISR：最多 60s 重生一次
export const revalidate = 60;
坑：没设 dynamic 时，Next 会“自动”推断——用到 cookies()/headers() 就变动态，否则尝试静态。这种隐式行为常让人困惑，关键页显式声明最稳。

5. RSC 深入

React Server Components（RSC）是 Next 的基石：组件默认在服务端运行，编译后不进客户端 JS 包。

  • 零客户端体积：直接 import 服务端 SDK、读数据库、读文件，这些代码用户浏览器根本拿不到。
  • 流式传输：用 <Suspense> 把慢的部分“先挂起”，页面先吐出骨架，数据到了再补，首屏更快。
  • 不是 SSR 的替代品：SSR 是把客户端组件在服务端跑一遍字符串；RSC 是“组件根本不发给客户端”。两者常结合。
心智模型：Server Component = 在服务端执行的异步函数，返回的是“UI 描述”而不是 HTML 字符串；框架把它和客户端部分拼起来流式下发。

6. 数据获取

在 Server Component 里直接 async/await 取数，不需要 useEffect：

async function getUser(id: string) {
  const res = await fetch(`https://api.x/u/${id}`, { next: { revalidate: 60 } });
  return res.json();
}
export default async function Page() {
  const user = await getUser('1');
  return <h1>{user.name}</h1>;
}
别混两层：服务端数据用 fetch 缓存/重验证管理；客户端交互状态才用 Zustand 之类。把服务端数据塞进全局 store 会导致缓存失控（见 React 第 8 节）。

7. Server Actions 与表单

Server Actions 让“提交表单 → 服务端改数据”无需手写 API：

'use server';
export async function createPost(formData: FormData) {
  const title = formData.get('title');
  await db.insert({ title });
  revalidatePath('/blog');   // 刷新缓存
}
// 页面里
<form action={createPost}><input name="title" /><button>提交</button></form>
好处：少一层 API 胶水、自带序列化、自动复用同一个请求上下文。配合 useFormState/useOptimistic 还能做渐进增强与乐观更新。

8. 客户端边界

需要用 useState、onClick、浏览器 API 时，把组件标 'use client'。这条边界决定代码跑在哪。

  • 默认是 Server：能不标 client 就不标，减少 JS 体积。
  • client 能 import server 吗？不能反向。Server Component 可以渲染 Client Component，反之不行。
  • 把 client 推到叶子：尽量只在最内层交互组件标 client，外层保持 server，避免整页变客户端包。
常见错：在 Server Component 里写 onClick 直接报错。任何事件/状态都要下沉到 'use client' 组件。

9. 缓存与重验证

Next 有四层缓存：请求记忆（同渲染内去重）、Data Cache（fetch 结果跨请求）、Full Route Cache（整页 HTML）、Router Cache（客户端导航）。理解它们才能不“改了不生效”。

要做的API
按 tag 失效一批revalidateTag('posts')
按路径失效revalidatePath('/blog')
关闭某请求缓存fetch(url, { cache: 'no-store' })
调试必记：本地开发默认不缓存，部署后才缓存——所以“我本地改了没事，线上不更新”多半是缓存没失效。先在 Server Action / Route 里显式 revalidate。

10. 样式方案

方案用法
CSS Modulesstyles.xxx，作用域隔离，默认就支持
Tailwind全局 globals.css 引入，见 Tailwind
CSS-in-JS需改用支持 RSC 的方案（如 styled-components 的 App Router 兼容版），否则有运行时坑
建议：全站用 design tokens（CSS 变量）+ 一套基础组件（或 Ant Design），改主题一处生效。

11. 中间件

middleware.ts 在请求进入路由前运行，适合鉴权、重定向、A/B、地区路由：

// middleware.ts
import { NextResponse } from 'next/server';
export function middleware(req: NextRequest) {
  const token = req.cookies.get('token');
  if (!token) return NextResponse.redirect(new URL('/login', req.url));
  return NextResponse.next();
}
export const config = { matcher: ['/dashboard/:path*'] };
边界：中间件跑在 Edge Runtime，不能用 Node 专属 API（如直接连某些 DB 驱动）。重型逻辑放 Route Handler / Server Action。

12. Route Handlers

需要传统 REST API 时，用 app/api/.../route.ts：

export async function GET(req: Request) {
  return Response.json({ ok: true });
}
export async function POST(req: Request) {
  const body = await req.json();
  return Response.json({ received: body }, { status: 201 });
}
选型：页面数据用 Server Component 直取；只有“被第三方调用 / 非页面消费”的接口才写 Route Handler，别什么都拆成 API。

13. 鉴权与安全

  • 会话：用 cookies() 读写 HttpOnly cookie；敏感操作校验签名。
  • CSRF：同站用 sameSite: lax 已基本挡住；跨站表单加 token。
  • 头部加固：在 next.config 配 CSP、X-Frame-Options 等。
  • 不要泄露：Server Component 里的密钥只在服务端，别传 props 给 client。
坑：把 NEXT_PUBLIC_ 前缀的环境变量会打进客户端包——绝不能放密钥。

14. 图片与字体

  • next/image：自动压缩、懒加载、响应式 srcset，并防布局抖动（固定宽高）。
  • next/font：字体在构建期自托管，避免阻塞渲染、无布局抖动、无隐私外泄。
性能信号：Lighthouse 的 CLS（布局抖动）几乎全靠这两件解决。

15. 性能优化

  • 减少 client 边界：Server 默认最省 JS。
  • 流式 + Suspense：慢数据不阻塞首屏。
  • 动静分离：能静态的页用 SSG/ISR，别全 SSR。
  • 包分析：@next/bundle-analyzer 找出大依赖；能用 server 处理的就别发到 client。

16. 部署

  • Vercel：零配置，自动识别 Next，推荐新手。
  • 自托管：output: 'standalone' 产出极小运行时，配合 Docker + Nginx 反代。
  • Node 服务：next start 用 PM2 守护。
自托管注意：中间件/Edge、ISR 磁盘缓存路径要在容器里正确挂载，否则缓存“丢了”。

17. 常见坑

坑 1 水合不一致：Server 与 Client 首渲 HTML 不同（如用了 Date.now()、随机数）会报警。固定输入或用 useEffect 补。
坑 2 误用 client：把整个页面标 'use client'，RSC 优势全无。只在交互叶子标。
坑 3 缓存不失效：改了数据页面不更新——忘了 revalidateTag/Path。
坑 4 在 Server 用浏览器 API：window/localStorage 在服务端是 undefined，必崩。

18. 何时不用

Next 有“框架税”：约定、缓存心智、构建复杂度。以下情况别上：

  • 纯内部工具后台，CSR + Vite 更轻更快。
  • 团队完全不懂 SSR/缓存，强行用会天天踩坑。
  • 超简单静态站，直接用静态生成或纯 HTML。

19. 调试与监控

  • React DevTools + Next Devtools 看 RSC 边界。
  • Build 日志：看每个路由是 static / dynamic / SSR。
  • 监控：Vercel Analytics / Web Vitals，关注 TTFB、CLS。
