React：从小白到资深前端

本教程不止教你“怎么写组件”，而是带你建立资深前端工程师的心智模型：理解它为什么这样设计、什么时候该用什么模式、性能与安全怎么权衡、怎么把小项目架构成能跑三年的系统。读完你能独立负责中大型前端工程。

1. 它解决什么问题

在 React 之前，前端是命令式的：拿到 DOM 节点，手动 innerHTML、appendChild 去改。状态一多，界面和数据很容易“对不上”。

一句话：React 把“界面”定义为状态的函数：UI = f(state)。你只描述“给定状态应该长什么样”，状态变了 React 负责把界面更新成对的样子。这就是声明式。

虚拟 DOM 与 Fiber（原理级，资深必懂）

  • 虚拟 DOM：React 用 JS 对象描述界面（vnode），状态变更后生成新树，与上一次树做 diff（Reconciliation），只把“变化的部分”打到真实 DOM。它解决的是“批量、最小化 DOM 操作”，而不是“比原生 DOM 快”。
  • Fiber 架构（React 16+）：把渲染拆成可中断、可恢复的“纤维”单元，配合优先级调度，避免大组件渲染卡住主线程（这是 Concurrent 特性的地基）。
  • 合成事件：React 不在每个节点绑事件，而是在根节点用事件委托，既统一又省内存，但也带来 e.target 与 nativeEvent 的区别。
资深视角：不要神话“虚拟 DOM 快”。它的价值是可预测的状态→UI 映射与跨平台（同一套组件可跑 Web/RN/SSR）。性能瓶颈几乎从不在 diff，而在不必要的重渲染与大列表。

2. 工程化起步

真实团队不会手写 index.html 引入 CDN，而是用构建工具 + 类型 + 规范三件套。

1

Node + 包管理器

装 Node.js LTS。推荐用 pnpm（快、省磁盘、严格依赖隔离）：npm i -g pnpm。

2

脚手架

pnpm create vite@latest app --template react-ts
cd app && pnpm i

react-ts 模板自带 TypeScript，资深项目几乎必用 TS——类型即文档，能在编译期挡掉大量 bug。

3

规范与质量门

pnpm add -D eslint prettier @typescript-eslint/parser
pnpm add -D husky lint-staged  # 提交前自动 lint

再加 editorconfig、commitlint。资深工程师的交付物不是“能跑”，而是“团队任何人都能安全接手”。

4

目录约定

src/
├─ app/         # 全局 provider、路由入口
├─ features/    # 按业务域划分（user/、order/）
├─ components/  # 通用 UI（Button、Modal）
├─ hooks/       # 自定义 Hook
├─ lib/         # 请求封装、工具
└─ types/       # 全局类型

按功能（feature）而非按文件类型组织，是项目变大后还能维护的关键（详见第 16 节）。

3. 心智模型

  • 单向数据流：数据从父经 props 往下流；要改数据，调父传下来的回调。避免到处能改同一份状态导致的“幽灵 bug”。
  • 不可变数据（Immutability）：永远产生新对象而非就地修改。setUser(u => ({...u, age: 19})) 而非 u.age = 19。React 靠“引用变了”判断要不要重渲染，就地改它“看不出来”。
  • 状态要放在“刚好够高”的地方：能不提升就不提升；兄弟共享才提到共同父级；全局才用 store。
反模式：“把所有状态塞进 Redux/localStorage”是新手到资深的第一个分水岭。状态位置错了，组件就耦合、难测、重写成本高。

4. JSX 与组件本质

JSX 不是模板，是 React.createElement 的语法糖，编译后就是普通 JS 调用。

// 下面这段 JSX
const e = <h1 className="t">Hi</h1>;
// 编译后等价于
const e = React.createElement('h1', { className: 't' }, 'Hi');
记住：组件本质是“返回 React 元素（或 null）的函数/类”。大写开头是为了区分原生标签。Props 是只读的——想改就回调通知父级。

组件类型选择：函数组件 + Hooks 已是事实标准；类组件只在维护老代码时见。新项目一律函数组件。

5. Hooks 深入

useState：批处理与函数式更新

// 连续两次更新拿旧值 → 只 +1；用函数式更新才正确
setCount(c => c + 1);
setCount(c => c + 1);
// 在事件处理里 React 18 自动批处理；在 Promise/setTimeout 里也默认批处理（18+）

useEffect：依赖、清理、竞态

useEffect(() => {
  let alive = true;                       // 取消标记，防卸载后 setState
  fetch(`/api/user/${id}`)
    .then(r => r.json())
    .then(d => { if (alive) setUser(d); });
  return () => { alive = false; };        // 清理：id 变化/卸载时作废旧请求
}, [id]);                                 // 依赖写实，否则闭包拿旧值
竞态：快速切换 id，慢的请求可能后到覆盖快的。上面的 alive 标记或 AbortController 是标准解法。

useMemo / useCallback / useRef

  • useMemo：缓存“昂贵计算结果”，依赖变才重算。别滥用——它自己也耗内存，简单计算不值得。
  • useCallback：缓存函数引用，配合 memo 子组件避免无谓重渲染。
  • useRef：存“可变但不触发渲染”的值（定时器 id、上一次值、DOM 节点）。注意改 .current 不会重渲染。

useReducer / useContext / 自定义 Hook

复杂状态（多字段、互相依赖的更新）用 useReducer 比一堆 useState 清晰。useContext 跨多层传值，但会让所有消费者重渲染——高频更新别走 Context。

function useToggle(initial = false) {            // 自定义 Hook：复用状态逻辑
  const [on, setOn] = useState(initial);
  return [on, () => setOn(v => !v)] as const;
}
规则：Hooks 只能在组件或自定义 Hook 顶层调用，不能在条件/循环里——这就是 Rules of Hooks，确保调用顺序稳定。

6. 渲染与性能

React 性能问题的 90% 是不该渲染的组件渲染了。触发渲染的只有两条路：自己 setState、父组件渲染。

  • 默认整条子树都重渲染。用 React.memo 包裹子组件，配合稳定的 props（靠 useCallback/useMemo）阻断。
  • key 不是“序号”：key 是 React 识别“谁是同一个节点”的身份证。用数组下标当 key，增删会导致状态错乱（输入框串内容）。用稳定业务 id。
  • 大列表用虚拟滚动：@tanstack/react-virtual，只渲染可视区，万级数据也不卡。
  • 代码分割：React.lazy + Suspense 把路由级页面拆成独立 chunk，首屏不下载全部代码。
  • 避免在渲染中创建新对象/函数：传给 memo 子组件的 inline 对象/箭头函数会让 memo 失效。
误区：“加 useMemo 一定更快”是错的。无谓 memo 反而增加比较开销。先用 Profiler 找到真实热点再优化（见第 18 节）。

7. 状态管理选型

没有“最好”，只有“最适合当前层级”。决策树：

场景选理由
局部 UI 状态useState就近放组件内
跨 2~3 层、不常变Context + useReducer免依赖，但注意重渲染范围
全局、高频、多模块Zustand / Jotai按 selector 订阅，精准更新；比 Redux 轻
强规范、可回溯、复杂团队Redux Toolkit单向流、devtools 时间旅行、可测试
资深经验：服务端数据不算客户端状态，别存进 Redux/store（见第 8 节）。客户端状态只放“UI 需要的”、无法从服务端重建的东西（当前选中项、表单草稿、主题）。

8. 服务端状态

“用户列表、订单详情”这类来自后端、要缓存/重试/失效的数据，交给 React Query (TanStack Query) / SWR，而不是自己写 useEffect + useState。

const { data, isLoading, error } = useQuery({
  queryKey: ['user', id],
  queryFn: () => fetch(`/api/user/${id}`).then(r => r.json()),
  staleTime: 60_000,
});

它自带：缓存、后台重新验证、请求去重、乐观更新（先改 UI 再等服务端确认）、分页/无限加载、失效重取。资深前端把“数据获取”和“UI 状态”彻底分清。

乐观更新：点赞立刻变红，失败再回滚——用 onMutate/onError/onSettled，体验与健壮性兼顾。

9. 路由

多页面用 react-router-dom（v6+ 是嵌套路由 + useRoutes 配置式）。关键点：

  • 懒加载路由：const User = lazy(() => import('./User')) 减小首包。
  • 鉴权路由：包一层 <RequireAuth>，未登录重定向到 /login，并记住来源 location.state。
  • 嵌套布局：<Outlet/> 让父布局（侧边栏）稳定，只换内容区，避免整页重挂载。

10. 表单与校验

受控组件（value + onChange）最直观但每个键击都渲染；高频/复杂表单用 react-hook-form（非受控 + ref，性能好）配合 zod 做 schema 校验：

const { register, handleSubmit, formState: { errors } } = useForm();
const onSubmit = (v) => save(v);
<input {...register('email', { required: true, pattern: /^\S+@\S+$/ })} />
{errors.email && <span>邮箱格式不对</span>}
坑：把整个表单放一个巨 useState 对象、每次按键全表重渲染——大表单会卡。用 RHF 或 uncontrolled。

11. 设计模式

  • 容器 / 展示分离（Container/Presentational）：容器管数据（取数、状态），展示只收 props 画 UI，易测、易复用。
  • 组合优于继承：用 children 或具名插槽（<Card.Header> 复合组件）拼装，而非层层 props 透传。
  • Pro props 透传（prop drilling）：超过 3 层还靠 props 往下传，就该用 Context 或把组件“上移”。
  • 自定义 Hook 抽逻辑：把“数据获取 / 防抖 / 键盘快捷键”等行为抽成 Hook，组件只关心渲染。
  • 错误边界（Error Boundary）：用 class component 的 componentDidCatch 或 react-error-boundary 包住子树，避免一个组件崩全盘白屏。

12. 样式方案

方案取舍
CSS Modules作用域隔离、零运行时，适合通用组件
Tailwind快、约束统一，但 JSX 变长；见 Tailwind
CSS-in-JS（styled）动态主题方便，但有运行时开销，SSR 需特殊处理
资深做法：用 design tokens（颜色/间距/字号集中定义成 CSS 变量）+ 一套基础组件库（或 Ant Design），保证全站视觉一致、改主题一处生效。

13. 测试体系

资深前端的交付包含测试，分层：

  • 单元/组件测试：Vitest + @testing-library/react，测“用户输入 → 界面变化”，不测实现细节。
  • Mock：用 MSW（Mock Service Worker）拦截请求，组件测试不依赖真后端。
  • E2E：Playwright 跑真实浏览器走完整流程（登录→下单）。
test('点击 +1 计数加一', () => {
  render(<Counter />);
  fireEvent.click(screen.getByText('+1'));
  expect(screen.getByText('计数：1')).toBeInTheDocument();
});
别测什么：别断言“有没有调某个函数”，测“用户能看到/做到什么”。实现重构后测试仍应绿。

14. SSR 与 Next.js

纯 CSR（客户端渲染）首屏慢、SEO 差。Next.js 提供：

  • SSR（每次请求服务端渲染）/ SSG（构建时生成）/ CSR 混合。
  • RSC（React Server Components）：组件在服务端跑、不进 JS 包，直接读数据库，零客户端体积——这是 React 当前最重要的演进方向。
Hydration 陷阱：SSR 输出 HTML 与客户端首渲必须一致，否则水合错位（如日期用 Date.now() 两边不同）。详见 Next.js。

15. 安全与 a11y

  • XSS：React 默认转义文本，安全；但 dangerouslySetInnerHTML 是后门——除非来自可信来源并 sanitize（用 DOMPurify），否则禁用。
  • 依赖供应链：pnpm audit、锁文件入库、CI 里跑 SCA，防恶意包。
  • 可访问性 a11y：语义化标签、aria-*、键盘可达（focus 管理、Esc 关弹窗）、颜色对比度。不是“加分项”，是合规与体验底线。

16. 大型架构

  • 按 feature 分包，而非 components/utils 平铺——域边界清晰，重构影响面小。
  • Monorepo（pnpm workspace / Turborepo）：把 web、共享组件库、后端 SDK 放一个仓库，跨包复用与原子提交。
  • 设计系统：把 Button/Input/Modal 抽成独立 package，全产品统一。
  • 微前端：多团队独立部署才考虑；否则是过度设计。先问“真有这么多独立团队吗”。
资深判断：架构是“为可预见的演化留余地”，不是“现在就上最重的方案”。过早微前端/DDD 是常见过度设计。

17. 资深也踩的坑

坑 1 陈旧闭包：useEffect 里用了外部变量却没进依赖，拿到旧值。解法：写全依赖 + useRef 存最新值，或用 useEffectEvent。
坑 2 无限重渲染：在渲染里 setState 新对象、或在 useEffect 依赖里放每次新建的数组 → 死循环。先创建再 set、依赖用原始值。
坑 3 状态囤积：把服务端数据塞全局 store，导致缓存/失效失控。交给 React Query。
坑 4 key 误用：用 index 当 key 做“可增删列表”，状态错位。用稳定 id。
坑 5 内存泄漏：组件卸载后 fetch 才返回再 setState 报错；事件监听/定时器没在 cleanup 移除。务必 cleanup。
坑 6 memo 失效：给 memo 子组件传 inline 新对象/函数，每次都是新引用，等于没 memo。

18. 调试与剖析

  • React DevTools：看组件树、props/state、高亮重渲染。
  • Profiler：记录一次交互的提交耗时，找出“谁渲染太久”。
  • React Scan / why-did-you-render：直接标出“不该渲染却渲染”的组件。
  • 网络/Performance 面板：定位长任务、卡顿帧、请求瀑布。
