better-sqlite3：从小白到资深后端

better-sqlite3 是 Node.js 上最快的嵌入式 SQLite 封装，最大特点是同步 API 与零配置单文件数据库（如 Memora 的生产存储就用它）。本教程讲透同步模型、预编译语句、事务、WAL 并发、跨平台原生模块与性能边界——何时用、怎么用、哪里会踩雷。

1. 它解决什么问题

相比 MySQL 要起服务、配账号、运维，SQLite 是个文件——开箱即用、零依赖、事务完备（ACID）。better-sqlite3 在此基础上做到“同步调用、原生速度”。

一句话：要“一个文件搞定持久化、又能扛事务”的单机/中小流量场景，SQLite 是首选；高并发写/需要网络共享则上 MySQL。
适合：CLI/桌面应用、个人项目、Demo、边缘/Serverless 本地存储、单写者业务。
不适合：高并发写（>数百 TPS 写）、多机共享数据。

2. 工程化起步

npm install better-sqlite3

它是原生模块（C++ 编译）：

  • 开发机需编译环境（Windows 装 VS Build Tools / 已带 python+node-gyp）。
  • 通常能拿到预编译二进制；CI 上若拉不到，用 npm rebuild better-sqlite3。
  • 跨平台部署陷阱：在 Mac 装好、部署到 Linux 要重新编译——务必在目标平台 npm install --ignore-scripts 后再 npm rebuild，或构建镜像里装。

3. 打开与模式

import Database from 'better-sqlite3';
const db = new Database('/abs/path/app.db');   // 用绝对路径，避免工作目录漂移
db.pragma('journal_mode = WAL');              // 开 WAL：读写可并发、崩溃更安全
db.pragma('foreign_keys = ON');               // 开外键约束
  • 内存库 new Database(':memory:') 用于测试/临时计算。
  • 只读打开 new Database('app.db', { readonly: true }) 防误写。

4. 建表与类型

db.exec(`
  CREATE TABLE IF NOT EXISTS user (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    age INTEGER
  );`);
SQLite 弱类型：列声明是“类型亲和”，理论上可存任意类型；但请按语义约束，避免脏数据。主键 INTEGER 自增走 rowid 优化，最快。

5. 预编译语句

用 prepare 编译一次、多次执行——既快又防注入：

const insert = db.prepare('INSERT INTO user(name, age) VALUES (?, ?)');
insert.run('小王', 18);                 // 参数绑定，杜绝 SQL 拼接注入
const one = db.prepare('SELECT * FROM user WHERE id = ?').get(1);

6. 事务

const insertMany = db.transaction((names) => {
  for (const n of names) insert.run(n);   // 整批原子、且比逐条快很多
});
insertMany(['a', 'b', 'c']);
// 出错自动回滚；可 db.transaction(...).deferred()/immediate() 控制锁时机
资深：批量写务必包进 transaction——不仅原子，还把多次 fsync 合并，性能翻倍。

7. 查询

  • .run() 写操作，返回 {changes, lastInsertRowid}。
  • .get() 取单行、.all() 取全部、.iterate() 流式遍历（大结果集不爆内存）。

8. 性能与并发

同步阻塞是核心约束：better-sqlite3 是同步 API，一次写会阻塞 Node 事件循环。注意：① 单条都快（微秒级），别在请求里做超大事务；② 真正并发写由 SQLite 的文件锁串行化——本质“单写者”。
  • WAL 模式：读不阻塞写、写不阻塞读，提升并发读；但写仍串行。
  • 提升吞吐：用事务批量、合理索引、避免 SELECT * 大行。

9. 迁移

自建迁移表记录版本，按顺序执行 up 脚本：

db.exec(`CREATE TABLE IF NOT EXISTS _migrations (v INTEGER)`);
const [{ v = 0 } = {}] = db.prepare('SELECT v FROM _migrations ORDER BY v DESC LIMIT 1').all();
// if (v < 2) { db.exec(...); db.prepare('INSERT INTO _migrations VALUES (2)').run(); }

10. 索引优化

  • 常查列加 CREATE INDEX；用 EXPLAIN QUERY PLAN 看是否走索引。
  • SQLite 也怕全表扫描；联合索引同样遵循“最左前缀”。

11. 常见坑

坑 1：同步写阻塞事件循环 → 大事务拆小、批量进事务。
坑 2：SQL 拼接 → 注入；用 ? 参数。
坑 3：多进程写同文件互相锁 → 单写者或用 WAL + 应用层排队。
坑 4：相对路径导致工作目录不同生成多个 db → 用绝对路径。
坑 5：跨平台部署原生模块没重编译 → 部署机 rebuild。
坑 6：大表无索引 → 查询慢；用 EXPLAIN QUERY PLAN 查。

12. 调试

  • 用 sqlite3 app.db CLI 直接查；PRAGMA integrity_check 查损坏。
  • PRAGMA table_info(user) 看表结构。

13. 成长路线

阶段能力标志
小白能建表、用预编译语句 CRUD
初级会事务、参数绑定、迁移
中级懂 WAL 并发、同步阻塞边界、索引
资深跨平台部署、容量与备份、与 MySQL 选型
练习：① 用事务批量插 1 万行并计时 ② 用 EXPLAIN QUERY PLAN 对比有/无索引 ③ 配 WAL 后开两进程读+写 ④ 写个迁移脚本加列 ⑤ 在 Linux 部署机 rebuild 原生模块。
你已进阶：理解同步嵌入式 DB 的能力边界与部署陷阱，能在“轻量单机存储”与“大型服务端 DB”间正确选型——这是资深对存储的务实判断。
