大模型 LLM：从小白到资深

LLM（大语言模型） 是用海量文本训练的“下一个词预测器”，是 RAG/Agent/客服的大脑。本教程讲透消息模型、参数精解、流式、上下文成本、可靠性工程与模型选型——这是用大模型做产品的地基。

1. 它解决什么问题

你发一段“提示（prompt）”，模型返回“合理的续写”。它本质是概率模型，所以同样的 prompt 也可能给出不同答案——这与传统确定性 API 不同，需要新的工程思维。

一句话：LLM 不是查数据库，而是“按概率生成”；可控性要靠 prompt + 参数 + 后处理共同保证。

2. 工程化与密钥

npm install openai
export OPENAI_API_KEY=sk-xxxx    # 只在服务端环境变量，绝不进前端/仓库
密钥红线：API Key 只在后端用、走环境变量；前端若直连会泄露被盗刷。用 供应商抽象 隐藏具体 SDK。

3. 消息模型

对话是一组有角色的 messages：

角色作用
system系统指令（人设/规则），最前，定调行为
user用户输入
assistant模型回复（多轮需回传以“记忆”）
tool工具结果（配合 Function Calling）
多轮必须回传完整历史：否则模型“失忆”。但历史会累积 token，需做截断/摘要（见 四层记忆）。

4. 关键参数

  • temperature：0 最确定（适合抽取/分类），越高越发散（适合创意）。
  • max_tokens：单次最多生成 token（≠上下文上限），设太小会截断。
  • top_p：核采样，控制候选词范围；与 temperature 二选一调。
  • frequency/presence penalty：抑制重复/鼓励新话题。
  • response_format: {type:'json_object'}：强制 JSON 输出，便于结构化解析。
  • stop：遇到指定串停止。

5. 流式输出

开 stream:true 后按 chunk 增量返回，配合 SSE 推前端做打字机：

const stream = await client.chat.completions.create({ model, messages, stream: true });
let full = '';
for await (const chunk of stream) {
  const d = chunk.choices[0]?.delta?.content || '';
  full += d;                      // 增量拼接
  res.write(`data: ${d}\n\n`);    // 经 SSE 推出
}

6. 上下文与成本

  • 计费按 token（输入+输出）算；长上下文/多轮会快速烧钱。
  • 上下文窗口有上限（如 8k/32k/128k/200k），超限报 400。
  • 对策：截断旧消息、摘要压缩、把长资料外置到 RAG 检索而非全塞。

7. 可靠性

  • 超时：设请求超时（如 30s），别让用户无限等。
  • 重试/退避：遇 429（限流）按指数退避重试；遇 5xx 重试。
  • 错误处理：解析失败、内容审核拦截要兜底，返回友好提示而非 500。

8. 模型选型

不必全用最强模型：规划/分类用便宜小模型，关键推理/生成用强模型（分层降本）。国产（智谱/DeepSeek/通义）在合规与成本上有优势——用 供应商抽象 便于切换与降级。

9. 常见坑

坑 1：Key 写死前端 → 泄露盗刷；走环境变量。
坑 2：多轮不回传历史 → 失忆。
坑 3：上下文超窗报 400 → 截断/摘要/RAG。
坑 4：temperature 太高导致确定性任务答乱 → 设 0。
坑 5：不同厂商参数/模型名直接搬运 → 用抽象隔离。
坑 6：没超时/重试 → 偶发失败即 500。

10. 调试

  • 打印每次的 token 用量（prompt_tokens / completion_tokens）做成本监控。
  • 记录入参出参与耗时，定位质量/延迟问题。
