TypeScript：从小白到资深类型工程师

TypeScript 是 JavaScript 的超集，给它加上静态类型。它不改变运行，只在编译期帮你挡掉一类“本来要等上线才爆”的 bug。本教程从“会写类型”讲到“用类型建模业务、设计可演进的 API”。

1. 它解决什么问题

JS 是动态类型：user.name 在运行时才发现 user 是 undefined。项目越大，这种“拼写错/结构变/传错参”的事故越多，IDE 也给不了靠谱提示。

一句话：TS 用类型即文档、类型即测试，把大量错误在写代码时就拦下，并让重构有安全感。
误区：TS 类型在编译后会被擦除，运行时没有类型保护。想运行时校验（API 入参），要配合 zod 这类 schema 库。

2. 工程化起步

pnpm add -D typescript
npx tsc --init          # 生成 tsconfig.json

关键配置（tsconfig.json）：

{
  "compilerOptions": {
    "strict": true,            // 一次开齐所有严格选项，资深项目必开
    "noUncheckedIndexedAccess": true,  // 访问 arr[i] 得到 T | undefined
    "target": "ES2022",
    "moduleResolution": "bundler"
  }
}
集成：Vite/Next.js 原生支持 TS，.ts/.tsx 直接写，无需额外配置；类型检查用 tsc --noEmit 接进 CI。

3. 类型基础

let age: number = 18;
const name: string = '小王';
const tags: string[] = ['a', 'b'];
const pair: [number, string] = [1, 'x'];   // 元组
let status: 'on' | 'off' = 'on';           // 字面量联合
新手：多用 const + 字面量类型，少用 any。any 会“关掉”该处类型检查，是技术债。

4. 接口与类型别名

interface User { id: number; name: string; email?: string }  // ? 可选
type ID = number | string;                                   // 别名可联合
type Point = { x: number; y: number };
interface vs type：interface 可被继承/声明合并（适合描述“对象形状/对外 API”）；type 能做联合/交叉/条件类型（适合组合）。团队约定统一即可，差别不大。

5. 函数与泛型

function first<T>(arr: T[]): T | undefined { return arr[0]; }
first([1, 2, 3]);           // T 推断为 number
first(['a']);               // T 推断为 string

// 约束：T 必须有 length
function logLen<T extends { length: number }>(x: T) { console.log(x.length); }
泛型本质：“类型层面的函数”，让代码对类型参数化而不丢失信息。库作者（如 React/Vue）几乎离不开它。

6. 高级类型

  • 联合 / 交叉：A | B（或）、A & B（且）。
  • 类型守卫：typeof/in/自定义 is 收窄联合类型。
  • 工具类型：Partial<T>（全可选）、Pick<T,K>、Omit<T,K>、Record<K,V>、Readonly<T>。
  • 映射类型：type Nullable<T> = { [K in keyof T]: T[K] | null }。
type User = { id: number; name: string; role: 'admin' | 'user' };
type PublicUser = Omit<User, 'role'>;           // 去掉敏感字段
type PatchUser = Partial<User>;                   // 更新时全可选
别走火入魔：“类型体操”很爽，但过度复杂的类型别人看不懂、编译也慢。类型服务于业务可读性，不是炫技。

7. 类与 OOP

class Service {
  private token: string;          // 私有，外部不可访问
  constructor(token: string) { this.token = token; }
  public call() { /* ... */ }
}
abstract class Animal { abstract speak(): void; }  // 抽象类
取舍：前端生态偏函数式；类适合“有状态、要封装行为”的对象（如 SDK 客户端）。接口优先于具体类，便于替换实现。

8. 严格模式心智

  • strictNullChecks：null/undefined 不能随便赋给非空类型——消灭“cannot read property of undefined”这一类头号运行时错误。
  • noImplicitAny：隐式 any 报错，逼你明确类型。
  • 非空断言 !：el!.value 告诉编译器“我保证非空”，但用错会运行时崩，慎用。

9. 声明文件

第三方没类型时，写 *.d.ts 声明模块；有社区类型就 pnpm add -D @types/xxx。还能做模块扩展（给已有库加字段），比改源码安全。

declare module 'legacy-lib' { export function doThing(): void; }

10. 与 React 结合

'use client';
interface Props { title: string; onClose: () => void; items: string[] }
function Modal({ title, onClose, items }: Props) {
  return <div><h2>{title}</h2>...</div>;
}
// 泛型组件
function List<T extends { id: number }>({ data }: { data: T[] }) { /* ... */ }
资深做法：用类型给组件 props/状态建模，配合 zod 在边界（API）做运行校验，形成“内外双保险”。

11. 常见坑

坑 1：any 瘟疫：一个 any 扩散，整条调用链失去检查。用 unknown + 类型守卫代替（unknown 强制你先收窄再使用）。
坑 2：以为类型能保证运行时安全——其实运行时无类型，外部输入必须 zod 校验。
坑 3：过度 enum：TS enum 会生成运行时对象、.tree-shaking 差，且反向映射易误导；倾向用 const 对象 + as const。
坑 4：类型与实现对不上（手改了接口忘了改实现）；用 implements 让编译器帮你对齐。
坑 5：循环类型依赖导致编译诡异；拆分共享类型到 types/。

12. 调试与工具

  • tsc --noEmit：只检查不编译，CI 必跑。
  • ts-node / tsx：直接跑 TS 脚本。
  • IDE 悬浮看推断类型、用 // @ts-expect-error 标记“故意的错误”。

13. 成长路线

阶段能力标志
小白会标基础类型、interface
初级泛型、工具类型、与框架结合
中级严格模式、声明文件、类型建模
资深用类型设计 API、约束业务规则、类型体操有度
练习：① 给一个 JS 项目全量加类型 ② 写泛型工具函数 ③ 用 zod 给 API 入参做运行校验 ④ 用 Omit/Pick 设计 DTO 分层（DB 实体 → API 返回 → 表单）。
你已进阶：能把业务规则“写进类型”，让编译器替你把门——这是资深工程师用 TS 的方式。
