WebSocket：从小白到资深实时后端

WebSocket 是 HTML5 的全双工通信协议：一次 HTTP Upgrade 握手后，服务端可随时主动向浏览器推数据，省去轮询。本教程讲透握手机制、帧与二进制、心跳、重连、鉴权、横向扩展与部署安全——这是理解一切实时通信（含 Socket.IO）的底层基础。

1. 它解决什么问题

HTTP 是“请求-响应”，服务端不能主动推。实时场景若用轮询，浪费连接与延迟。WebSocket 在单个 TCP 连接上做双向通道，连上后双方随时互发。

一句话：轮询是“客户端反复问”，WebSocket 是“连上后服务端有消息直接推”。
适合：行情推送、实时监控、游戏、消息通知。
注意：它是底层协议，无重连/房间/广播，要自己实现或上 Socket.IO。

2. 工程化起步

浏览器端原生支持，无需依赖；服务端用 Node 的 ws 库（轻量）或 Node 原生 http 手写。

npm install ws   # 生产级 WS 服务端库

生产务必用 wss://（基于 TLS），等同 HTTPS 对实时通道的加密。

3. 协议握手

WebSocket 始于一次 HTTP 请求，带 Upgrade: websocket 头与服务端用 Sec-WebSocket-Key 计算 Sec-WebSocket-Accept 回应 101 状态码，之后协议切换为 WS 帧。

资深：握手是普通 HTTP → 鉴权可借 Cookie/Authorization 头（见第 8 节）；反代必须放行 Upgrade（见第 11 节）。

4. 消息与帧

  • 数据封装为帧（frame）：文本帧（UTF-8）/ 二进制帧（ArrayBuffer/Blob）/ 控制帧（ping/pong/close）。
  • 客户端发往服务端的帧必须掩码（mask）（防缓存污染），服务端回的不掩码。
  • 大消息会被分片（fragment），库一般会帮你重组，但要留意单帧/单消息上限配置。

5. 收发与序列化

// 浏览器端
const ws = new WebSocket('wss://你的域名/ws');
ws.onopen = () => ws.send(JSON.stringify({ type: 'chat', text: 'hi' }));
ws.onmessage = (e) => { const obj = JSON.parse(e.data); };
// Node ws 服务端收到的 data 是 Buffer
ws.on('message', (data) => console.log(data.toString()));
  • WS 只传字符串/二进制，对象要先 JSON.stringify；用二进制可减体积（如 Protobuf）。
  • 接收端判断 typeof e.data 区分文本/二进制。

6. 心跳保活

长空闲连接会被代理/系统/NAT 回收，需定期“证明还活着”：

// 应用层心跳：每 30s 互发 ping/pong
const timer = setInterval(() => {
  if (ws.readyState === WebSocket.OPEN) ws.send('ping');
}, 30000);
ws.onmessage = (e) => { if (e.data === 'pong') resetTimeout(); };
要点：用应用层心跳 + 超时断开，比单纯依赖 TCP keepalive 更可控；超时未收到 pong 即视为断线。

7. 重连

原生 WS 不自带重连，要在客户端实现：

  • 指数退避：断线后 1s、2s、4s… 重连，避免雪崩式重试。
  • 状态机：区分 connecting/open/closing/closed，避免重复连接。
  • 重连后需重新鉴权、重新订阅房间（状态不保留）。

8. 鉴权

握手是 HTTP，所以可借 Cookie 或 Authorization 头/查询参数校验：

wss.on('connection', (ws, req) => {
  const token = new URL(req.url, 'http://x').searchParams.get('token');
  if (!verify(token)) ws.close(4001, 'unauthorized');  // 握手期即拒绝
});
别在 WS 消息里才鉴权：连接即资源，握手阶段就该校验；且身份以服务端为准，禁止客户端自报。

9. 横向扩展

WS 无内置广播/房间。多实例时：

  • 粘滞会话（Nginx ip_hash）让同用户落同节点；但节点挂了连接全丢。
  • Redis pub/sub：节点间转发广播事件（同 Socket.IO 思路）——更健壮的方案。

10. 安全

  • origin 校验：拒绝非白名单来源，防跨站 WS。
  • 消息体积上限：ws 可设 maxPayload，防超大帧打爆内存。
  • 限流：连接频率/消息频率节流，防 DoS。
  • 全程 wss 加密，防中间人窃听/篡改。

11. 部署

Nginx 反代必须放行 Upgrade，否则握手 400：

location /ws {
  proxy_pass http://backend;
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection "upgrade";
  proxy_read_timeout 3600s;   # 长连接别被默认超时切掉
}

12. 对比 Socket.IO

WebSocketSocket.IO
重连/降级自己写内置
房间/广播自己实现内置
依赖原生零依赖需引库
可控性最高封装好
选型：要极致可控/轻量/对接非 JS 端 → 原生 WS；要快速做聊天/协作/游戏且省心 → Socket.IO。

13. 常见坑

坑 1：Nginx 没放行 Upgrade → 握手 400。
坑 2：ws 收到的是 Buffer，忘 toString() 看到乱码。
坑 3：页面 https 但 WS 用 ws:// → 被浏览器拦，改用 wss://。
坑 4：不重连 → 网络波动后消息发不出。
坑 5：不设 maxPayload → 超大消息 OOM。
坑 6：心跳缺失 → 代理静默断开，连接“假活”。

14. 调试

  • 命令行 wscat -c wss://你的域名/ws 手动收发。
  • Chrome DevTools → Network → WS 看帧；Wireshark 抓帧级数据。
